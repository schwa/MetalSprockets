# RFC 0004: Metal 4 rendering

**Status:** As-built design record.

This RFC describes the current Metal 4 implementation. It is not a migration plan or a proposal for another backend.
The [porting guide](../Documentation/Porting-to-Metal4.md) covers changes required in client code.

## Decision

MetalSprockets composes Metal operations through a SwiftUI-style element tree. It does not introduce a second public model for command recording.

The tree describes passes, pipelines, bindings, draws, dispatches, and synchronization. The root owns submission and presentation.
Internal helpers manage resource lifetimes and reuse. They do not expose slots, allocation leases, or unsubmitted recording objects.

The backend requires macOS 26, iOS 26, or visionOS 26 and a device with `MTLGPUFamily.metal4` support.
There is no Metal 3 fallback. Immersive rendering requires a physical visionOS device.

## Element composition

Existing element identity, state, environment, and setup/workload traversal remain the foundation.
Pipeline compilation belongs to setup. Per-frame command encoding belongs to workload traversal.

| Element or modifier | Metal responsibility |
| --- | --- |
| `RenderPass` | Begin and end an `MTL4RenderCommandEncoder` |
| `ComputePass` | Begin and end an `MTL4ComputeCommandEncoder` |
| `RenderPipeline`, `MeshRenderPipeline`, `ComputePipeline` | Compile/cache a pipeline and publish its reflected bindings |
| `Draw`, `ComputeDispatch` | Bind inputs and issue work |
| `RenderCommand`, `ComputeCommand` | Provide raw encoder access, including pipeline-free work and copies |
| `.parameter`, `.vertexBuffer`, `.vertexValues` | Populate argument tables and retain declared inputs |
| `EncoderBarrier`, `QueueBarrier`, `.barrierAfterPass` | Express command dependencies |

Environment command buffers, queues, encoders, and descriptors use Metal 4 types.
Raw encoder closures are escape hatches, not an alternative submission mechanism.
They must declare resources that the framework cannot discover from bindings or attachments.

## Submission and scheduling

A root encodes and submits one command buffer per submission.

```swift
let runner = try Runner(maximumInFlightSubmissions: 3)
let submission = try runner.submit(content)
let result = try await submission.value()
```

`Runner.submit` encodes and commits before returning a `Submission`. It does not wait for that submission to finish.
`Runner.run` also waits and throws if GPU work does not complete successfully.
There is no `Runner.record`, `RecordedSubmission`, or deferred `commit`/`discard` API.

`Submission` is a completion handle for work already on the queue. Dropping the handle does not cancel GPU work.
`SubmissionResult.submissionIdentifier` identifies commit order within the root. There is no separate recording identifier.

`maximumInFlightSubmissions` is explicit execution policy, not a resource-pool size exposed under another name.
It must be positive and defaults to 3.

| Root | Behavior at the limit |
| --- | --- |
| `Runner` | Block until earlier work permits another submission |
| `RenderView` | Skip the frame rather than block the display callback |
| `ImmersiveRenderContent` | Await capacity before entering the compositor submission interval |

`Runner.submit` can therefore block for earlier work even though it returns before its own work completes.
The limit bounds outstanding submissions. It is not a byte limit on scratch storage, pipeline caches, or client resources.

Runners and encoding contexts stay on one isolation domain. They are not thread-safe or `Sendable`.
`Submission` is `Sendable`. Canceling an asynchronous waiter does not cancel its GPU submission.

## Command resources and completion

The internal context owns the device, queue, completion event, pipeline caches, and residency tracker.
Each active command buffer has an allocator, scratch storage, and reusable argument tables.
`Metal4CommandResources` groups these objects for ownership. It has no public identity or independent submission lifecycle.

Resources are allocated on demand. Successful retirement makes them available for reuse.
There is no indexed slot pool, generation counter, or capacity-exhaustion error for normal submission pressure.

The internal `Metal4RecordingScope` remains an encoding helper. It collects retained resources, prevents nested encoders, and rejects use after encoding ends.
It is not a returned recording object and cannot defer submission.

The submission path is:

1. Apply the root's in-flight limit and reject a faulted context.
2. Obtain reusable command resources, or allocate them.
3. Begin the Metal command buffer and traverse the element tree.
4. End encoding and establish residency for declared resources.
5. Commit the command buffer and signal the completion event.
6. Reuse storage only after successful feedback and the completion event both arrive.

An encoding error unwinds the encoders and ends the command buffer without submission.
Its resources can be reused because no GPU work references them.
The visionOS compositor can end the command buffer itself. The framework must not end it twice.

Successful completion requires both `MTL4CommitFeedback` and the shared-event notification. Either can arrive first.
A GPU error or an enforced timeout produces one terminal result and faults the context.
Faulted work is excluded from resource reuse. There is no automatic recovery or legacy fallback.

Context waits use a finite deadline, currently five seconds by default. `Submission.value()` does not install its own deadline.
A timeout does not prove that the GPU stopped accessing memory.

## Residency and ownership

Residency, object retention, and execution ordering are separate responsibilities.
A resident resource is not necessarily ordered against another command that accesses it.

Automatic residency covers declared client allocations for their submitted use.
Bindings and attachments retain their resources. Raw closures require `.useResource(s)` or `.useComputeResource(s)` for undiscoverable resources.
Memoryless attachments are retained but are not added to residency sets.

Persistent resources use `ResourceCollection`:

```swift
let resources = try ResourceCollection(device: device)
try resources.register(buffer)
let residency = ResidencyConfiguration(collections: [resources])
let runner = try Runner(device: device, residency: residency)
```

Registration is idempotent. Unregistration removes membership for future submissions immediately.
Resources remain resident while earlier submissions still require them. Encoding failure or successful GPU completion releases that use.
Failed or timed-out work does not release resources as though it completed successfully.

Framework-owned scratch storage, offscreen targets, MSAA targets, stencil targets, and visible-function tables use persistent residency.
`RenderView` also maintains a collection for its non-memoryless depth/MSAA attachments.
Resize and sample-count changes replace membership without invalidating earlier submissions.
Drawable textures use the `CAMetalLayer` residency set rather than this collection.

Clients can supply existing residency sets through `ResidencyConfiguration`.
Covered allocations, including resources within registered heaps, do not enter the automatic tracker again.
Clients must commit their sets and preserve membership through GPU use. The framework cannot defer client changes to raw sets.

Manual mode disables automatic residency for client allocations, not retention or residency for framework-owned storage.
It does not remove the need for resource declarations in raw closures.

## Pipelines, shaders, and arguments

`MTL4Compiler` creates pipelines from explicit shader provenance: library, function name, stage, constants, and optional specialized export name.
`ShaderFunction` preserves that information. A raw `MTLFunction` alone is not the pipeline input contract.
Typed shaders and linked/visible functions use this provenance.

Pipeline caches account for shaders, specialization, attachment formats, sample count, vertex layout, linked functions, and labels as applicable.
Render attachment formats come from the pass, not depth/stencil fields on a Metal 4 pipeline descriptor.

Reflection maps parameter names to stage, binding kind, and index.
Each draw or dispatch obtains cleared argument tables. Later commands cannot inherit bindings for omitted parameters or unused texture-array entries.
Sparse binding indices determine table capacity. Vertex streams supplied by layout index also contribute to that capacity.

Scalar and array values use the scratch storage described below. Values must be `BitwiseCopyable`.
Samplers require argument-buffer support. Residency does not make an unset required binding valid.

Argument-table labels combine the pipeline label and stage, such as `Cube: Vertex Arguments`.
Unlabeled pipelines use the `MetalSprockets` prefix. Metal makes these labels immutable, so table reuse is keyed by capacity and label.

## Scratch storage for shader values

`.parameter(value:)`, `.parameter(values:)`, and `.vertexValues` copy Swift values into GPU-readable shared `MTLBuffer` storage during encoding.
Argument tables bind the buffer's GPU address plus the allocation offset. The GPU reads a copy, not the original Swift value or array.
Later changes to the Swift data do not change that copy.

Each reusable command buffer/allocator pair owns a `Metal4ScratchArena` through `Metal4CommandResources`.
Overlapping submissions use separate arenas. Draws and dispatches within one submission reserve separate regions as they encode their values.
The arena does not overwrite earlier regions during that submission.

### Allocation and growth

The arena uses bump allocation: each reservation advances an offset within the current buffer.
Alignment is the greater of the value's required alignment and 16 bytes. Explicit alignment must be a positive power of two.
Empty allocations are rejected.

Buffers are allocated on demand. The internal initial capacity defaults to 4,096 bytes.
If the current buffer cannot fit an allocation, the arena tries its remaining cached buffers before allocating another buffer.
A new buffer's capacity is the largest of:

- Twice the previous buffer's length.
- The requested byte count plus alignment.
- The configured initial capacity.

Growth appends buffers rather than replacing existing storage. Addresses already bound during encoding remain valid.
Large values can therefore allocate a larger buffer immediately. There is no fixed maximum allocation size imposed by the arena.

### Residency and reuse

The arena registers its buffers in a persistent `ResourceCollection`.
Each submission retains the scratch resources it uses through GPU completion.
Scratch storage does not require repeated automatic residency registration each frame.

After successful retirement, reuse resets the buffer index and byte offset. It does not clear buffer contents or release cached buffers.
New allocations copy fresh bytes into their reserved regions. Padding and unused bytes are not guaranteed to be zero.
An encoding failure also permits reuse because the command buffer was not submitted.
Failed or timed-out GPU work does not permit reuse.

### Memory cost and caller control

Repeated value bindings still copy bytes each frame, even when no new Metal buffers are needed.
Each arena retains its allocated buffers at their high-water capacity. It has no automatic shrinking or memory-pressure trimming.
Separate arenas can reach different peak sizes, so total retained memory includes the capacity of every cached arena.
The in-flight submission limit is not a scratch-memory budget.

Buffers are released when their owning arena is released, subject to outstanding resource references.
The context can discard whole cached command-resource groups when the in-flight limit decreases. That does not shrink arenas it keeps.

Clients do not manage individual scratch allocations. For explicit storage ownership, persistent data, or independent update schedules, use buffer bindings instead.
`.parameter(buffer:)` and `.vertexBuffer` bind caller-owned buffers without copying their contents into scratch storage.
Clients remain responsible for preventing CPU writes while GPU work uses those buffers.

These allocation sizes and growth rules describe `Metal4ScratchArena.swift`. They are internal implementation choices, not public API guarantees.

## Synchronization and presentation

The framework does not infer data dependencies from the element tree or resource declarations.

- `EncoderBarrier` orders dependent commands within a pass.
- `QueueBarrier` expresses a consumer dependency on earlier encoders on the same queue.
- `.barrierAfterPass` emits a producer barrier before ending the pass.
- Cross-queue dependencies require explicit Metal events.

For drawable presentation, the queue waits for the drawable, commits rendering, and signals the drawable before presentation.
The context signals its completion event after the presentation sequence.
Immersive rendering uses the compositor's Metal 4 queue and presentation APIs.

## Callbacks and diagnostics

`onSubmissionCommitted` reports CPU-side submission, not GPU start. Its notification precedes terminal notification.
`onCommandBufferCompleted` reports the terminal `SubmissionResult`. Encoding failures do not produce a GPU completion result.
The isolation-aware overload delivers through a task on the caller's isolation domain.

`onSubmissionFinished` also covers encoding failure and timeout. It is not, by itself, proof of successful GPU completion.
Clients must not treat a timed-out result as permission to overwrite memory still accessible to the GPU.

Submission GPU timing comes from commit feedback. Missing or invalid timing remains absent rather than becoming a fabricated zero duration.
`.gpuCounters` provides pass measurements. It does not provide a separate Metal 4 fragment interval.

Pass labels identify encoders. Pipeline labels identify pipeline states and argument tables.
Capture scopes wrap whole passes. Shader logging is configured per root and disables capture for the process.

## Deliberate limits

- No Metal 3 fallback or mixed Metal 3/4 command-buffer submission inside an element tree.
- No public unsubmitted recording object, replay contract, or GPU cancellation API.
- No implicit hazard tracking or automatic cross-queue synchronization.
- No guarantee that all MPS APIs can encode into a Metal 4 command buffer.
- No promise that a terminal error means GPU resources are safe to reuse.

The [Metal 3 interop RFC](0004-metal3-interop.md) discusses separate future work. It is not part of this implementation.

## Verification and implementation references

Tests cover GPU output, argument-table clearing and labels, overlapping submissions, encoding errors, cancellation, timeout, residency, and attachment replacement.
Hardware-dependent tests use `.requiresMetal4`. Passing CI on a device without Metal 4 support is not evidence of GPU correctness.
Metal API Validation on supported hardware supplements ordinary tests and platform builds.
