# RFC 0002 — Metal 4 Support

**Status:** In Progress (Steps 0–2 + Parameters complete; 3+ pending)
**Author:** schwa
**Date:** 2026-04-18 (revised mid-rewrite)
**Tracking issue:** #256
**Background:** `~/Shared/Notes/WhatsNewInMetal4.md` (general Metal 4 overview)

## Summary

Reimplement MetalSprockets on Metal 4. Drop Metal 2/3. Bump minimum
platforms to macOS 26 / iOS 26 / visionOS 26. Breaking change at the
*Metal* level; the *MetalSprockets public API* turned out to translate
almost unchanged (see "Migration impact" below).

This RFC is **Phase 1** of a two-phase strategy. See "Strategy"
below. Backwards compatibility with Metal 2/3 is explicitly out of
scope here and not planned as an RFC until after Phase 1 ships.

## Migration impact (added mid-rewrite)

Upfront, the RFC framed this as a redesign of the public API. In
practice the public surface barely shifted:

- `BlitPass` is gone.
- `Draw` and `ComputeDispatch` closures lost the second
  `pipelineState` argument; the framework now sets the PSO for you.
- `.barrier(...)` and `.useResource(_:)` are new modifiers users may
  need to add explicitly.
- Several internal types (`Reflection`, `ShaderCache`,
  `LibraryRegistry`, `MTLCommandQueueCompletion`) are gone.
- `ShaderLibrary` collides with SwiftUI's same-named type; users
  qualify as `MetalSprockets.ShaderLibrary`.

Everything else — `RenderView`, `RenderPass`, `RenderPipeline`,
`ComputePipeline`, `Draw`, `ComputeDispatch`, `.parameter(_:buffer:)`
/ `.parameter(_:texture:)` / `.parameter(_:value:)`, `ShaderLibrary`
bundle/source loading, typed shader wrappers, `Group`, `ForEach`,
`@MSState`, `@MSEnvironment` — reads identically. Real porting effort
for an existing user is small. The framing of "redesign the public
surface" was wrong; it should have been "reimplement the backend
beneath an essentially-stable surface."

## Strategy: two phases

The previous attempt at Metal 4 support tried to build a
legacy-compatible abstraction up front. That failed — design
questions about the abstraction kept getting entangled with "does
this still work on Metal 2/3?" The Metal 4 shape never got to
emerge.

New plan:

- **Phase 1 (this RFC).** Drop Metal 2/3 entirely. Rebuild
  MetalSprockets on pure Metal 4. Breaking change. Learn what the
  natural Metal 4 shape actually is. Phase 1 is broken down into
  implementation *Steps* (see "Implementation steps" below).
- **Decision point at the end of Phase 1.** With a working Metal
  4-only MetalSprockets and real API shapes in hand, decide whether
  a Metal 2/3 compatibility path is worth building. Inputs:
    - Who (if anyone) is actively using MetalSprockets on pre-Metal
      4 hardware.
    - How alien the natural Metal 4 shapes turned out to be.
    - Whether argument tables / `MTL4Archive` / `MTL4Compiler` can
      be approximated on Metal 3 without reshaping the public API.
- **Phase 2 (possible future work; no RFC yet).** Only if Phase 1
  and the decision point say yes. Likely follows Apple's own
  side-by-side pattern (Metal 3 renderer + Metal 4 renderer as
  sibling implementations with a shared public interface), not a
  hybrid abstraction. No RFC for this will be written until Phase 1
  has shipped and been used.

If the decision point says no: we stay Metal 4-only. Apple's own
sample ships Metal 3 and Metal 4 as parallel implementations rather
than behind an abstraction; that's a defensible long-term shape for
us too.

## Why

Metal 4 is a model change, not an API change. `Experiments/Metal4HelloTriangle`
and a research pass through the WWDC 2025 Metal 4 sessions + Apple's
`metal-drawing-a-triangle-with-metal-4` sample identified five shifts:

1. **Command model.** `MTL4CommandBuffer` comes from an
   `MTL4CommandAllocator`. One buffer is reused across frames; a pool
   of N allocators rotates per in-flight frame. Frame pacing is via
   `MTLSharedEvent`, not per-buffer completion handlers.
2. **Encoder model.** Two encoder classes instead of three. Compute
   now absorbs blit + acceleration-structure commands.
3. **Binding.** `MTL4ArgumentTable` replaces per-stage
   `setBuffer`/`setTexture`.
4. **Residency.** Manual, via `MTLResidencySet`. `CAMetalLayer`
   provides its own dynamic residency set the queue attaches once.
5. **Hazard tracking.** Manual, via explicit barriers
   (`barrierAfterStages:beforeQueueStages:visibilityOptions:`).

Each of these reaches into what is currently public API
(`Draw`, `Blit`, `onCommandBufferCompleted`, …). A clean Metal 4
implementation redesigns that public surface rather than hiding the
new shapes behind old ones.

## Non-goals

- Supporting Metal 2/3. Out of scope.
- Preserving public API. Opportunity to redesign anything shaped by
  assumptions that no longer hold on Metal 4.
- New Metal 4-only features (MetalFX 4, ML dispatch, tensors, sparse
  resources, color attachment mapping, suspend/resume render passes).
  Follow-on work after the core is running.
- A `BlitPass`-as-separate-encoder in the new API. Blit is a compute
  command in Metal 4.

## Platform & availability

- **Minimum:** macOS 26 / iOS 26 / visionOS 26.
- `Package.swift` platforms updated.
- No `@available` gates on individual types; the whole library
  assumes Metal 4.

## Key design decisions

### Command buffer lifecycle

One `MTL4CommandBuffer`, reused every frame. Three
`MTL4CommandAllocator`s in a pool (matches Apple's sample; enough for
triple-buffering).

Per frame:

1. Compute `frameIndex = frameNumber % 3`.
2. If `frameNumber > 3`, wait on `MTLSharedEvent` for signal
   `frameNumber - 3`.
3. `allocators[frameIndex].reset()`.
4. `commandBuffer.beginCommandBuffer(allocator: allocators[frameIndex])`.
5. Encode everything.
6. `commandBuffer.endCommandBuffer()`.
7. `queue.waitForDrawable(drawable)`.
8. `queue.commit([commandBuffer])`.
9. `queue.signalDrawable(drawable)`.
10. `drawable.present()`.
11. `queue.signalEvent(sharedEvent, value: frameNumber)`.

`CommandBufferElement` wraps the whole sequence. User-visible
modifiers (`onCommandBufferScheduled`, `onCommandBufferCompleted`) are
implemented by attaching completion handlers to the `MTLSharedEvent`
at the appropriate signal values — **not** via `MTL4CommitOptions`
feedback handlers. Simpler, and the natural fit for the
environment-values model.

### Encoders

Two encoder types in the environment: `MTL4RenderCommandEncoder` and
`MTL4ComputeCommandEncoder`. Stored directly — no wrapper, no
abstraction.

Note: `drawIndexedPrimitives` takes `indexBuffer:` as an
`MTLGPUAddress` (a `UInt64`, typically `buffer.gpuAddress + offset`)
and `indexBufferLength:` in bytes — not an `MTLBuffer` + offset pair.
This will surprise users porting from the old MetalSprockets.

Elements:

- `RenderPass` → `MTL4RenderCommandEncoder`
- `ComputePass` → `MTL4ComputeCommandEncoder`
- `BlitPass` — **becomes a thin wrapper around `ComputePass`** that
  only permits blit-stage commands, or is deprecated entirely in
  favor of doing blit work inside a regular `ComputePass`. Open
  question.

`Draw` / `ComputeDispatch` user closures take Metal 4 encoder types
directly. No mirrored protocol. No escape hatch. Users write
`encoder.drawPrimitives(primitiveType: .triangle, …)` exactly as in
the Metal 4 API.

### Binding: `MTL4ArgumentTable` and Parameters

This is the largest piece of new code in Phase 1 and got the
thinnest treatment in the original RFC. Treat this section as a
sub-RFC.

**Surface.** The user-facing API is the existing `.parameter(_:...)`
modifier family, unchanged in shape:

```swift
Draw { encoder in encoder.drawPrimitives(...) }
    .parameter("vertices", buffer: vertexBuffer)
    .parameter("uniforms", value: uniforms)
    .parameter("environment", texture: envMap)
    .parameter("linearSampler", sampler: sampler)
```

**Mechanism.**

1. `RenderPipeline` / `ComputePipeline` compile with
   `MTL4PipelineOptions.shaderReflection = .bindingInfo` at
   `setupEnter` time.
2. The pipeline walks the resulting reflection (`vertexBindings` +
   `fragmentBindings` for render; `bindings` for compute) and builds
   a `PipelineBindings` value: a `name → [(stage, kind, index)]`
   map plus one `MTL4ArgumentTable` per stage that has any
   bindings. Tables are sized per stage as `max(index) + 1` for
   each of buffer / texture / sampler. The pack is stashed in the
   environment.
3. `.parameter(_:buffer:|texture:|sampler:|value:)` modifiers run
   between the pipeline and its child `Draw` / `ComputeDispatch`.
   At `workloadEnter` they look up the name in the reflection map,
   validate kind, write the right slot of the right table, and
   register `MTLBuffer` / `MTLTexture` arguments with the residency
   set automatically.
4. `Draw` / `ComputeDispatch` set the pipeline state and bind each
   stage's argument table on the encoder before invoking the user's
   closure.

**Argument tables: one per stage**, not shared. Decided. The
`MTLRenderStages` mask supports stage-shared tables, but per-stage
is simpler to size from reflection and matches Apple's samples.

**Per-frame value uniforms.** `.parameter(_:value:)` accepts any
value type. The value is copied into a `ScratchBufferPool` owned by
`CommandBufferLifecycle`: one `.storageModeShared` `MTLBuffer` per
in-flight frame slot, bump-allocated, reset at `beginFrame`. If a
frame's allocations exceed the slot's capacity it grows on the fly;
retired backing buffers are held alive until the slot is recycled
so GPU addresses already handed out remain valid for the in-flight
frame. **All scratch buffers must be in the residency set** — the
pool registers each new buffer (initial and grown) with the
lifecycle's root residency set automatically. Forgetting this was a
real bug during Step 2d that produced silent zero reads with no
warning.

**Failure modes.** Type mismatches throw at workload time. Names
that don't match anything in reflection log a warning and skip.
Both are runtime-only signals; there is no compile-time check that
parameter names exist in the shader.

**Bind-count maxima** (per Metal 4): buffer ≤ 31, texture ≤ 128,
sampler ≤ 16 per table. Reflection sizes never exceed these in
practice.

### Residency (this is a discipline, not a feature)

The original RFC treated residency as a property to enable. After
building it, residency is better understood as a **discipline that
touches every code path that hands a buffer or texture to the GPU**
— user-supplied or framework-internal. Failure mode on Apple Silicon
is silent zero reads. There is no validation-layer warning unless
the user has Metal API Validation on. This shaped Step 2d (a missing
residency entry on the framework's *own* scratch buffer pool was the
bug that almost killed Parameters — zero reads, no diagnostic, took
a while to find).

**Architecture.**

- `CommandBufferLifecycle` owns a root `MTLResidencySet` attached
  to the queue once at init.
- The lifecycle exposes `registerResource(_:)` /
  `registerResources(_:)` and adds the set's `commit()` for the
  caller. Both are idempotent.
- The `ScratchBufferPool` registers its own buffers (initial set
  and any grown ones) with the residency set.
- `CAMetalLayer.residencySet` is attached **per command buffer**
  (`commandBuffer.useResidencySet(...)`), per the Xcode 26 Metal 4
  Game template. The layer manages its own contents.
- `.parameter(_:buffer:)` and `.parameter(_:texture:)` register the
  argument with the lifecycle automatically.
- `.useResource(_:)` / `.useResources(_:)` modifiers register
  user-supplied resources passed by hand inside `Draw` /
  `ComputeDispatch` closures.

**Invariant (enforce via review).** Any `MTLAllocation` the
framework binds via an argument table or encoder call must pass
through lifecycle registration. A future refactor should consolidate
all binding through a single `lifecycle.useGPUResource(_:)`
chokepoint that registers and returns the resource, so that
residency is a precondition of binding rather than something that
can be forgotten.

**Notes.**

- `MTLSamplerState` is **not** an `MTLAllocation`. Don't put it in
  a residency set.
- `MTL4ArgumentTable` itself is not an allocation either.
- The framework should default to enabling Metal API Validation in
  development builds (a scheme tweak in examples/experiments) to
  make residency mistakes visible.

### Barriers

Metal 4 does no automatic hazard tracking between encoders.
MetalSprockets surfaces this as an explicit
`.barrier(afterStages:beforeStages:visibilityOptions:)` modifier the
user places between producing and consuming encoders. This matches
Apple's own samples and the Xcode 26 Metal 4 Game template; neither
infers.

**Inferred barriers** — the framework recording per-encoder resource
use and inserting barriers automatically on write-then-read — are a
stretch goal, not part of Phase 1. Reasons:

- The failure mode for an incorrect inferrer is silent pixel
  corruption, identical to a forgotten explicit barrier but sneakier
  because the user has been told the framework handles it.
- Over-barriering kills the perf win that motivates Metal 4.
- Cross-pipeline aliasing and partial-resource access make false
  negatives and false positives both easy to write.

If inference ever ships it lives in Step 6 or 7 and gates on a test
harness that can prove correctness across non-trivial graphs.

### Pipelines

Built with `MTL4Compiler` + `MTL4RenderPipelineDescriptor` /
`MTL4ComputePipelineDescriptor`. `ShaderCache` replaced with a
Metal 4-native cache. Pipeline specialization (unspecialized →
specialized for different color attachment states) is a Step 5
feature.

### visionOS / CompositorServices

Metal 4 is fully supported on visionOS 26 via CompositorServices
(WWDC25-294). The existing `immersiveRenderContext` integration path
survives — `renderContext.endEncoding(commandEncoder:)` still exists,
but takes an `MTL4RenderCommandEncoder`. Step 4 verifies; no
architectural uncertainty.

Metal 4-only visionOS features (hover effects, dynamic render
quality, progressive immersion, `queryDrawables()` array return) are
Step 7+.

## Failure model (read this before Implementation steps)

Metal 4 on Apple Silicon is largely **silent on bugs**. Nearly every
class of mistake renders something plausible instead of crashing or
logging. The framework should be designed assuming that fact:

- Forgetting residency → GPU reads zeros.
- Forgetting a barrier between encoders → GPU reads stale data.
- Mismatched argument-table slot → GPU reads adjacent garbage.
- Buffer overrun → GPU reads adjacent garbage.
- Wrong stage in `setArgumentTable(_:stages:)` → silent miss.

Consequences for design:

- Maximize compile-time safety (typed shader wrappers, typed
  parameter modifiers).
- For runtime checks, prefer *loud and on-by-default* over silent
  best-effort. Log warnings for unmatched parameter names; throw
  for type mismatches; log on shared-event timeouts.
- Recommend Metal API Validation on in development. Default it on
  in example/experiment schemes.
- Single chokepoints for residency and binding so the framework's
  own internals can't accidentally bypass safety (the scratch-buffer
  residency bug in Step 2d was exactly this kind of self-inflicted
  miss).

## Implementation steps

Phase 1's implementation is broken into Steps. Each Step starts and
ends at a working state. **Prefer keeping the package green; delete
files only as their replacement lands.** The original RFC plan of
"rip out everything in Step 0, rebuild from scratch" was tried and
produced a long broken-package window for no benefit. Incremental
deletes worked vastly better in practice.

### Step 0 — clear the decks

- Bump `Package.swift` to macOS 26 / iOS 26 / visionOS 26.
- Delete only files that have no Metal 4 equivalent and aren't
  blocking compilation downstream (e.g. `BlitPass`).
- Other Metal 2/3 code is left in place to be replaced as later
  steps land.

### Step 1 — command lifecycle on Metal 4

Rewrite `CommandBufferElement` around the
`MTL4CommandAllocator` / `MTL4CommandBuffer` /
`MTL4CommandQueue` / `MTLSharedEvent` pattern above.

- Environment stores `MTL4CommandBuffer` + `MTL4CommandQueue`.
- Triple-buffered allocator pool, `kMaxFramesInFlight = 3`.
- Frame pacing via `MTLSharedEvent`.
- `onCommandBufferCompleted` / `onCommandBufferScheduled` reshape to
  take just a `CommandCompletionInfo` struct (label, GPU timings if
  available, status). Implementation registers handlers on the shared
  event.
- Root `MTLResidencySet` attached to the queue; also attach the
  `CAMetalLayer`'s residency set when there's a view.
- Encoder/pipeline elements are also rewritten in Step 1 as a
  prerequisite for Step 2's verification — in practice the
  lifecycle isn't testable in isolation. Originally the RFC said
  Step 1 ended at a buildable lifecycle with no encoders; this was
  honored, but "no encoders" left the only tests as Core-only and
  the lifecycle effectively unverified until Step 2 landed. Keep
  the staging order but treat Steps 1 and 2 as a single merge
  rather than independent shipping units.

### Step 2 — encoders + pipelines + parameters + HelloTriangle parity

*This is secretly four steps; the RFC originally treated it as one.
In practice the work fell out as substeps a–g, each a sensible
commit boundary.*

- **2a.** Shader types, `ShaderLibrary`, `RenderPipeline`,
  `ComputePipeline` via `MTL4Compiler`.
- **2b.** `RenderPass` + `Draw` on `MTL4RenderCommandEncoder`.
- **2c.** `ComputePass` + `ComputeDispatch` on
  `MTL4ComputeCommandEncoder`.
- **2d.** `Parameters` (see Binding section above) — reflection,
  per-stage `MTL4ArgumentTable`s, `.parameter(...)` modifiers,
  scratch buffer pool. The biggest single substep.
- **2e.** Residency-set growth + `.useResource(_:)` /
  `.useResources(_:)` modifier.
- **2f.** Explicit `.barrier(afterStages:beforeStages:visibilityOptions:)`
  modifier for hazard tracking. Inference deferred (see "Barriers"
  above).
- **2g.** Port `Experiments/Metal4HelloTriangle` to MetalSprockets
  and render the same compute-gradient triangle. **Visual
  verification is the only real signal here**; tests can't tell you
  if pixels are right.

`BlitPass` decision: gone. Done in Step 0 instead of deferred.

### Step 3 — port surviving elements

This is going to fragment hard — these elements have very different
shapes. Sub-RFC each as you go if any of them turn out non-trivial.

- `OffscreenRenderer`, `OffscreenVideoRenderer` (a sub-step on its
  own; needs an offscreen Metal 4 lifecycle without `RenderView`).
- `MetalFXSpatial`, `MetalFXTemporal`.
- `MeshRenderPipeline` (object + mesh shaders).
- `VisibleFunctionTableModifier`.
- `CaptureModifier` (`.capture(...)`).
- Debug labels / debug groups.
- visionOS `ImmersiveRuntime` / `ImmersiveRenderPass` /
  `ImmersiveRenderContent`.
- iOS `ARKitSessionModifier`.
- `Example/` target rebuilt against Metal 4.

Each lands with tests — ideally golden-image tests where the element
has visual output (see Testing section).

### Step 4 — platform verification

- macOS 26, iOS 26 example apps running.
- visionOS 26 immersive app running via CompositorServices + Metal 4.
- CI matrix on macOS and iOS.

### Step 5 — pipeline performance

Follow-on after Step 4 ships.

- `MTL4Archive` on-disk pipeline cache. First-run compile-and-write;
  subsequent runs load-from-disk. Key includes OS/Metal versions +
  descriptor + source hashes.
- Ahead-of-time compilation support: harvest pipeline scripts via
  `MTL4PipelineDataSetSerializer`, build archives with `metal-tt`,
  look up at runtime with `archive.makeRenderPipelineState(descriptor:)`.
  MetalSprockets provides the runtime-lookup side; harvesting is a
  developer-side workflow.
- Flexible render pipeline states (unspecialized → specialized).
  Surface as an opt-in modifier or as automatic behavior when a
  pipeline group is detected. Open question.

### Step 6 — residency polish

- `.residencySet(.automatic)` / `.residencySet(.manual(_))` modifiers.
- Audit resource ownership; ensure transient allocations leave the
  set.
- Documentation for user-facing behavior.

### Step 7 — new Metal 4-only features

Parallelizable after Step 4. No ordering between these.

- `MetalFXFrameInterpolator`
- `MetalFXDenoisedUpscaler`
- Reactive mask input on `MetalFXTemporal`
- `MachineLearningDispatch` (`MTL4MachineLearningCommandEncoder` +
  `MTLPackage` / `MTLTensor`)
- Color attachment mapping element / modifier
- Suspend/resume render passes (multi-threaded encoding)
- Texture view pools
- Placement sparse resources
- visionOS 26 hover effects, dynamic render quality, progressive
  immersion
- `MTL4Counters` hook (touches #50; probably its own RFC)
- Tile shading parity
- macOS-to-Vision-Pro spatial rendering

## Documentation

Documentation hasn't kept up with the rewrite. Two pieces are owed
before Phase 1 can be called done:

- **Porting guide.** Wait until the rewrite is actually finished
  (Steps 3+4 land); then write a single migration article showing
  every public-API change with before/after for each. An attempt
  written mid-Step-2 was abandoned: half the page was "not done
  yet" placeholders and at least one section invented Metal 4 API
  renames that don't exist. Don't write this guide piecemeal.
- **Sample/example docs.** The existing DocC articles
  (`GettingStarted.md`, `Comparison.md`, `Architecture.md`,
  `FAQ.md`, `Tutorials/`) and the `Example/` app still describe
  Metal 2/3 APIs that no longer exist. They need a sweep against
  the final Metal 4 surface, not the in-progress one.

## Testing

The original RFC said "test pass-rate is a real progress metric."
That turned out to be wishful: most of the deleted code's tests went
with it, and the 64 passing tests after Step 2 were Core-only —
*zero of them verify that the Metal 4 graph actually renders
correctly*. Visual verification by a human was the only signal that
Step 2 worked.

This is unacceptable for Step 3 onward. **Golden-image tests must
land with each Step 3 element.** The blocker is `OffscreenRenderer`
on Metal 4 — without it, golden-image tests can't run headless.
Prioritize porting `OffscreenRenderer` first within Step 3 so the
rest of Step 3 can land with proper coverage.

What to test:

- Command-recording lifecycle: allocator recycling across 3 frames,
  shared-event completion signals firing, residency-set membership.
- Argument-table slot assignment via reflection (build a pipeline,
  apply parameters, dispatch, read back via offscreen target).
- Pipeline reflection name lookup, including missing-name and
  type-mismatch error paths.
- Scratch buffer pool grow-mid-frame: GPU addresses returned before
  the grow remain valid through frame end.
- Per-element golden images for every Step 3 element.
- Manual visual verification on macOS / iOS / visionOS for Step 4.

## Risks

- **User migration.** Existing users hit a breaking upgrade.
  Acceptable given pre-1.0 status, but document the migration.
- **Barrier inference completeness.** Miss a write-then-read pair and
  the user gets undefined output. Explicit modifier is the escape
  valve; inference needs to be right for common cases.
- **Argument-table sizing.** Reflection must return correct maxima
  per pipeline, or we over/under-size.
- **Residency ownership.** Who owns which allocation, who removes it
  when. Fiddly. Step 2's automatic-growth path needs careful design.
- **MTLSharedEvent timing.** `waitUntilSignaledValue:timeoutMS:` with
  a real timeout — what do we do on timeout? Apple's sample just
  logs. MetalSprockets probably should too, but document.
- **SDK churn.** Metal 4 APIs may still shift in dot releases.

## Open questions

Resolved during the rewrite:

1. ~~`BlitPass`~~ — deleted in Step 0.
2. ~~Argument-table sharing~~ — one per stage. Decided in Step 2d.
3. ~~Completion-info signature~~ — `CommandCompletionInfo { label,
   frameIndex }`. GPU timings deferred until we wire
   `MTL4CommitFeedback` (separate task).

Still open:

4. Shared-event timeout handling — log + continue, or surface an
   error? Currently logs; revisit if it becomes a real failure mode.
5. `MTL4Archive` cache path and versioning strategy for Step 5.
6. Whether to rename `ShaderLibrary` to avoid the SwiftUI collision
   (a breaking-rename, but kept as `MetalSprockets.ShaderLibrary`
   in the meantime).
7. Whether the future residency chokepoint is a single
   `lifecycle.useGPUResource(_:)` call or a property-wrapper-style
   `@GPUResident` declaration. Either works; design when Step 6
   lands.

## After Phase 1

The decision point described in "Strategy" above. No follow-on RFC
exists or is planned until Phase 1 has shipped and we can judge from
evidence rather than speculation.

## Appendix: notes from the rewrite

Pragmatic things the rewrite agent learned, kept here so the next
person doesn't repeat them.

### Where to look first

- `Experiments/Metal4HelloTriangle/Metal4HelloTriangle/Renderer.swift`
  is a complete working Metal 4 demo (compute + render in one
  command buffer, three argument tables, explicit barrier, residency
  set). It's the canonical reference for how Metal 4 code should
  look on the inside; mirror its patterns.
- Apple's own sample is `cupertino read-sample
  metal-drawing-a-triangle-with-metal-4`. When in doubt about an
  API name or pattern, check there before guessing.
- The Metal 4 SDK headers under
  `/Applications/Xcode-*/.../Metal.framework/Headers/MTL4*.h` are
  ground truth for protocol shapes. `rg` through them when Swift-
  bridged names are unclear. **Do not invent renames** — most of
  what feels like "Metal 4 renamed X" is the same Objective-C
  selector as Metal 3, bridged to the same Swift signature.

### Things that burned the rewrite

- **No automatic hazard tracking.** If encoder A writes a resource
  and encoder B reads it, you must encode an explicit
  `barrier(afterStages:beforeQueueStages:visibilityOptions:)`. The
  failure mode is silent corruption (magenta noise, stale gradients,
  zeroed reads).
- **No automatic residency.** Every `MTLAllocation` the GPU reads
  must be in an `MTLResidencySet` attached to the queue or command
  buffer. Failure mode on Apple Silicon: zero reads, no warning.
  Run with Metal API Validation on. `MTLSamplerState` is not an
  `MTLAllocation`. `CAMetalLayer` has its own dynamic residency set
  — attach it per command buffer.
- **Allocator count is `maxFramesInFlight` (3), not 4.** Apple's
  Xcode 26 Metal 4 Game template's `(0...maxBuffersInFlight).map`
  produces 4; that's an off-by-one in the template. The triangle
  sample and WWDC25-254 both use 3.
- **Frame-pacing init.** `frameIndex = maxFramesInFlight` and
  `endFrameEvent.signaledValue = UInt64(maxFramesInFlight - 1)`.
  First frame's wait-value is then `0`, already satisfied. Without
  this the first 3 frames hang.
- **The barrier method lives on the base `MTL4CommandEncoder`
  protocol**, not on the specific encoder. If Swift can't see it,
  cast to `any MTL4CommandEncoder` first.

### Decisions that were left open and have since been made

- **`BlitPass`** — gone. Metal 4's compute encoder absorbs blit
  commands. Use `ComputePass` / `ComputeDispatch` for blit work.
- **Argument-table sharing** — one table per stage. Vertex and
  fragment do not share.
- **`CommandBufferLifecycle` class** — kept. See "Why there's a
  class" below.

### Why there's a class (`CommandBufferLifecycle`)

Metal 3 MetalSprockets didn't need this type. Metal 4 does. The
reason, bluntly: Metal 4 inverted the command-buffer ownership
model.

On Metal 3, `CommandBufferElement` called
`commandQueue.makeCommandBuffer()` fresh every frame, ran the
frame, committed, and threw the buffer away. Everything interesting
lived on a short-lived value: the buffer carried its own completion
handlers, the encoders ended when the closure returned, there was
no per-frame counter because each buffer was independent. Pure
value types + env values worked because there was nothing long-
lived to reference.

Metal 4 replaces that with:

1. **One** `MTL4CommandBuffer` reused across every frame.
2. A **triple-buffered allocator pool** rotating per in-flight
   frame (`allocator.reset()` mutates the same instance).
3. A **long-lived** `MTLSharedEvent` with a monotonic signal value.
4. Explicit **residency** through a long-lived `MTLResidencySet`
   attached once to the queue.
5. An **`MTL4Compiler`** shared across every pipeline.
6. A **scratch buffer pool** (per-in-flight-frame ring) needed
   because `.parameter(_:value:)` writes to an argument table via
   `setAddress` rather than `setBytes`.
7. **Completion-handler lists** that `.onCommandBufferCompleted {
   ... }` modifiers append to and `endFrame` drains.

None of (1)–(7) fit in env values (a value dictionary children
read). They need a shared reference someone mutates across frames.
`CommandBufferLifecycle` is that reference — one instance per root
(`RenderView`, `OffscreenRenderer`, `OffscreenVideoRenderer`,
`Element.run()`), placed in the environment as
`\.commandBufferLifecycle` so descendants can find it.

The name is imperfect: the class and its owning `System` have the
same lifetime, so "lifecycle" suggests more than the type actually
is. Candidates for a future rename if the opportunity arises:
`CommandBufferContext`, `MetalRenderer`, or keeping the name and
owning the misnomer.

A possible alternative architecture is to push the class into
`@MSState` on a Root element rather than having roots own it
directly. That would more closely mirror Metal 3 MetalSprockets's
value-type aesthetic. It still requires a class somewhere (the
allocator pool can't be immutable). Open for later refactor.

### What not to do

- **Don't use `MTL4CommitOptions.addFeedbackHandler`** for basic
  `onCommandBufferCompleted`. `MTLSharedEvent` listeners are
  simpler and match Apple's pattern.
- **Don't hand-build `MTL4RenderPassDescriptor`** for `MTKView`
  rendering. `view.currentMTL4RenderPassDescriptor` auto-populates
  from the drawable and the view's depth/stencil settings.
- **Don't write a porting guide piecemeal.** An attempt mid-Step-2
  was abandoned because half of it was placeholders for unfinished
  work and one section invented Metal 4 "renames" that don't
  exist. Wait until the rewrite is finished.
